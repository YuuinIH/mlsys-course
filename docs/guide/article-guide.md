# 文章写作建议

这是一份轻量参考，**不是必须填满的统一模板**。文章的结构应该服从它想回答的问题。

## 先确定问题

动笔前试着回答：读者会多理解什么？需要什么解释与证据？结论在哪些条件下成立？相较于官方文档或现有教程，这篇文章为何值得写？

课程以系统机制、资源约束、可测量现象和工程权衡为中心，不追求讲完某个工具的 API。

## 难度与成熟度

- **L1 Fundamentals**：为有 CS 本科基础的读者建立完整直觉。
- **L2 Engineering**：具体机制、实现、测量及工程权衡。
- **L3 Advanced**：复杂设计、论文与开放问题。

难度不等于质量或重要性，也不强求每个主题凑齐三级。建议在 Markdown frontmatter 标记 `level`、`status` 和 `topics`，并如实区分**初稿、待验证、可学习**。只有提纲的文件不应进入正式文章索引。

## 形式由内容决定

概念文章可以没有代码；架构文章可以侧重源码与设计文档；实验文章可以包含假设、预测、观察与局限；技术史与论文讨论也可以独立成立。

写作中至少努力交代 **问题、解释、边界和延伸联系**，清楚区分事实、推断与待验证假设。不要为了整齐强行使用统一八段式。

## 实践为什么存在

只有在实践能够帮助理解、挑战直觉或检验机制时才安排动手活动。需要实验时说明环境、输入、测量方法与不确定性；但**不强制 Lab、作业、Decision Record 或大型项目**。

可以使用 AI 辅助生成代码与实验分析，但仍需要检查代码和证据的真实性、结论的适用条件。

文章可读后更新[专题索引](/essays/)与[主题地图](/topics/)；只有适合学习顺序时才加入[路径](/paths/)。
