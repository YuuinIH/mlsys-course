# 章节模板

除课程序章外，每章都要完成一次从问题到决策的调查循环。标题优先写成事故现象或设计问题，而不是技术名。序章可以使用连续故事建立共同问题，但仍应明确课程的调查方法以及进入下一章的理由。

## 1. Incident / Problem

用一个可观察的事件开场，例如：

> 集群监控显示还有 8 张空闲 GPU，但训练任务已经 pending 20 分钟。

说明受影响的人、目标指标和已知约束。不要在开场直接给结论。

## 2. Workload Characterization

回答当前 workload 的形状：

- 生命周期：训练、推理、部署还是运行？
- 目标：吞吐、延迟、收敛时间、可用性还是成本？
- 资源：计算、显存、内存、存储、网络还是调度配额？
- 负载：稳定、突发、长运行、同步密集还是多阶段？

## 3. Mental Model

只引入能帮助估算、形成直觉或做 sanity check 的理论。给出变量、单位、假设和适用边界；不要为了完整而复制数学教材。

需要本科知识时使用：

> **CS Refresher**：用几句话回顾缓存、虚拟内存、网络、控制循环或排队，并说明它如何影响当前问题。

## 4. System Mechanism

从证据出发解释相关机制，例如 GPU 内存层次、collective communication、Kubernetes reconciliation、KV cache 或 scheduler behavior。只讲能解释当前现象的部分。

可选细节放进：

> **Deep Dive**：主线不要求掌握的内核、协议或实现细节。

## 5. Hands-on Experiment

实验应当 **toy-scale, production-shaped**，并包含：

1. 问题与可证伪假设。
2. 环境、版本、输入和关键参数。
3. warmup、重复次数、同步方式和统计方法。
4. 原始结果摘要与图表。
5. 对异常值和测量局限的说明。

易变的安装、命令和 API 操作放进 **Cookbook**。提供低算力核心路径；只有现象确实需要时才增加 GPU 或集群路径。

## 6. Engineering Trade-offs

至少写清楚：

| 方案 | 获得 | 牺牲 | 适用条件 | 新风险 |
| --- | --- | --- | --- | --- |
| 待比较 | 待补 | 待补 | 待补 | 待补 |

用 **Reality Check** 说明实验规模与真实系统之间哪些结论可迁移、哪些可能失效。

## 7. Decision Record

以一个简短决策收尾：

- 选择什么，为什么？
- 哪些证据支持它？
- 拒绝了哪些方案？
- 哪个条件变化时需要重新评估？

## 8. 作业与参考

一个必做题复现核心现象，一个选做题改变假设或规模。参考资料按它回答的问题组织，不按工具名堆放。

## 提交前自查

- 是否由问题而不是工具名驱动？
- 是否区分症状、瓶颈、机制和决策？
- 是否有可复查的测量设计？
- 是否明确收益、代价、边界和新风险？
- 是否避免把 toy-scale 实验包装成生产经验？
