# 贡献指南

课程目前最需要的是清楚、可复现、能支持工程决策的内容。一次失败的实验、一张可信的指标表或一个更准确的问题，都可能比新增一段工具介绍更有价值。

## 调查主线

贡献内容应尽量完成这条循环：

```text
问题 -> 观察 -> 测量 -> 建立思维模型 -> 理解机制
     -> 实验 -> 评估取舍 -> 做出决策
```

动笔前先回答：

1. 发生了什么事件，或者必须做什么设计选择？
2. workload 的目标、输入分布、状态和资源特征是什么？
3. 哪些证据能区分竞争性假设？
4. 哪个机制解释了观测结果？
5. 方案获得什么、牺牲什么，并引入什么新风险？

## Problem First

不要以“介绍 Kubernetes / NCCL / vLLM / Prometheus”为目标。可以让这些技术出现，但要先有需要它们解释或解决的问题。

不推荐：

> 本章介绍 vLLM 的主要功能和参数。

推荐：

> 长 prompt 请求正在拖慢短请求。我们用 vLLM 观察 prefill、decode、KV cache 和调度如何影响 TTFT 与 ITL。

工具、API 和命令可能快速变化，应放在 **Cookbook**；稳定的思维模型与机制留在主线；不影响主线的底层细节放在 **Deep Dive**。

## 章节结构

除课程序章外，遵循[章节模板](chapter-template.md)：

1. Incident / Problem
2. Workload Characterization
3. Mental Model
4. System Mechanism
5. Hands-on Experiment
6. Engineering Trade-offs
7. Decision Record

用 **CS Refresher** 回顾解决当前问题所需的本科概念，用 **Reality Check** 说明 toy-scale 实验与真实系统之间的迁移边界。

## 实验要求

实验应当 toy-scale, production-shaped，并记录：

- 可证伪假设与成功指标
- CPU、内存、GPU、系统和主要软件版本
- 模型、数据、输入规模、batch、并发等关键参数
- warmup、同步、重复次数和统计方法
- 原始结果摘要、异常值和不确定性
- 对瓶颈的解释、备选解释和下一项验证
- 生产规模下可能失效的假设

没有 GPU 也可以贡献核心实验。GPU 或集群路径只有在关键现象无法用低算力路径表达时才作为必要条件。

## 参考资料

按问题组织资料，并说明每条资料支持哪个机制、估算或实验设计。不要只堆链接，也不要让引用替代自己的证据与推理。

正文尚未完成时，保留：

```md
## 作业与参考

> 待补：本章实验、作业和支持关键机制的参考资料。
```

## 状态

- **占位**：只有问题、实验方向和预期产出。
- **初稿**：已有可读正文，仍缺实验或证据。
- **待实验验证**：关键解释等待复现或复查。
- **可学习**：正文、实验、边界和参考均完整。

状态变化只需更新[学习地图](learning-map.md)中的汇总表和章节页本身。

## 提交前自查

- 标题是否由问题而不是工具名驱动？
- 是否区分症状、瓶颈、机制和决策？
- 估算是否写明变量、单位、假设和边界？
- 实验是否可复查，结论是否与证据匹配？
- 是否写清收益、代价、适用条件和新风险？
- 是否避免声称 toy-scale 实验等同于生产经验？
- 学习地图、导航、链接和文档构建是否正常？
