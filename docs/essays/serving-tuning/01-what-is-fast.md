# 1. 推理服务性能测量

> **L2 · Engineering** · **初稿** · 推理系统 / 性能与测量。本文关注如何评价推理服务的表现；具体的瓶颈定位和参数选择不在这里展开。

上一篇文章中，我们认识了 Orca、vLLM 和 SGLang，也知道了为什么一个能够运行大语言模型的程序，不一定是一个合格的推理服务。

现在，假设我们已经在实验室的一台 GPU 服务器上部署了 vLLM。模型正常加载，HTTP 接口能够访问，几个同学也成功调用了我们的服务。一切看起来都很顺利。

直到使用的人逐渐多了起来。

> “为什么每次都要等好久才能开始回答？”
>
> “我这里还好啊，就是回答到一半经常卡一下。”
>
> “你们这个服务只能给几个人用吗？人多一点就不行了？”

这就有点麻烦了。

他们抱怨的都是性能问题，却未必是同一种性能问题。第一个人关心模型什么时候开始回答；第二个人关心生成过程是否流畅；第三个人则关心这台服务器究竟能够服务多少人。

如果我们打开 `nvidia-smi`，发现 GPU 利用率已经达到 100%，然后宣布系统性能已经优化到极致，恐怕没有人会满意。GPU 忙不忙，并不能直接回答他们的问题。

在开始调整参数之前，我们首先需要弄清楚一件事：

**对于一个 LLM 推理服务，到底什么叫“快”？**

## 用户究竟在等待什么？

先考虑最简单的情况：只有一个用户在使用我们的服务。

用户向聊天机器人发送一个问题，等待模型生成回答。如果使用流式输出（Streaming），用户不必等到整个回答生成完毕，而是可以逐步看到新内容。

让我们把这个过程展开：

```text
客户端                         推理服务器
  │                                │
  │ ─────── 发送请求 ────────────► │
  │                                │
  │                         请求处理与排队
  │                                │
  │                             Prefill
  │                                │
  │ ◄────── 第一个 Token ───────── │
  │                                │
  │                              Decode
  │ ◄────── 第二个 Token ───────── │
  │                                │
  │                              Decode
  │ ◄────── 第三个 Token ───────── │
  │                                │
  │                               ...
  │ ◄────── 最后一个 Token ─────── │
  │                                │
请求完成
```

上一节已经提到，自回归语言模型通常需要不断生成下一个 Token。这个过程可以大致分为两个阶段：**Prefill** 处理输入 Prompt，计算相应的中间状态；**Decode** 则利用已有状态，逐步生成后续 Token。

不过，这两个词描述的是模型的执行过程，而用户感受到的等待时间还包括排队、网络传输等开销。从用户的角度，我们至少可以区分几种不同的等待。

### 第一个 Token 什么时候出现？

从客户端发出请求，到收到第一个有效输出 Token 的时间，通常称为 **Time to First Token（TTFT）**。

对于聊天机器人来说，TTFT 直接影响用户发送问题以后，需要等待多久才能看到模型开始回答。如果 TTFT 很长，即使后面的文本生成得非常快，用户仍然可能觉得服务反应迟钝。

不过，**TTFT 并不等于 Prefill 的执行时间**。它还可能包括网络传输、服务端排队、输入处理，以及其他运行时开销。

例如，模型处理很长的 Prompt 需要更多时间，可能导致 TTFT 增加；服务器正忙于处理其他请求时，排队也可能导致 TTFT 增加。这两种现象在用户看来非常相似，背后的原因却不同。

### 为什么回答到一半会卡顿？

收到第一个 Token 以后，模型会继续生成后续内容。对于流式输出，我们可以观察相邻 Token 到达客户端的时间间隔，称为 **Inter-Token Latency（ITL）**。

如果模型能够持续、均匀地生成 Token，用户看到的文本就比较流畅；反过来，如果生成过程中突然出现长时间停顿，即使模型最终完成了回答，也可能影响使用体验。

但我们不一定每次都需要逐个检查 Token 的间隔。有时，只是想了解一次回答的平均生成速度。

因此，性能测试中还经常使用 **Time Per Output Token（TPOT）**。一种常见的定义是：从收到首 Token 到最后一个 Token 的时间，除以首 Token 之后生成的 Token 数量。

\[
TPOT=\frac{T_{\text{total}}-TTFT}{N_{\text{output}}-1}
\]

这里，`T_{\text{total}}` 是整个请求的端到端延迟，`N_{\text{output}}` 是输出 Token 数量；公式假设至少生成了两个 Token。

这实际上做了一件很简单的事：把首 Token 之后的总耗时，平均分配给剩余 Token。

例如，某次回答在首 Token 之后，相邻 Token 的到达间隔是：

```text
50ms → 50ms → 250ms → 50ms
```

它的 TPOT 为 100ms，但实际输出并不均匀。中间那次 250ms 的停顿，仍然可能被用户察觉。

因此，TPOT 适合描述单个请求的平均生成速度，而 ITL 的分布可以进一步揭示生成过程中的波动。不同工具对流式输出事件和 Token 的统计口径可能不同，尤其是一次流式事件包含多个 Token 时，不能直接把两者等同起来。<sup>[[1]](#ref-vllm-benchmark)</sup>

### 整个回答需要多久？

还有一个更直观的问题：从发送请求，到收到完整回答，究竟经过了多长时间？这就是 **End-to-End Latency（端到端延迟）**。

对前面采用的流式测量方式，可以写成：

\[
T_{\text{total}}=TTFT+(N_{\text{output}}-1)\times TPOT
\]

这个关系提醒我们：**一个请求需要等待多久，不仅与模型生成得多快有关，也与它究竟生成了多少内容有关。**

一个只回答“你好”的请求，与一个需要生成几千个 Token 的请求，即使使用相同模型，端到端延迟也可能相差很大。所以，如果不说明输入和输出长度，直接比较两个推理服务的延迟，参考价值就很有限。

以上讨论主要针对流式输出。如果客户端只能在回答完成后一次性收到结果，那么客户端看到的首次响应时间，也不能直接当作模型生成首 Token 的时间。

## 一个人很快，不代表服务器很快

现在，我们能够描述单个请求的响应体验了。

假设这台 GPU 在只有一个用户使用时，每秒能够生成 50 个 Token。这听起来还不错。

可是，如果服务器同时收到十个请求呢？

一种简单的处理方式是依次处理每个请求。这样，正在运行的用户可能依然感觉很流畅，但后面的用户必须等待前面的请求完成。

我们也可以尝试把多个请求组织起来，让 GPU 同时处理更多工作。如果调度得当，服务器单位时间内完成的工作可能增加，但每个用户分到的计算资源也会发生变化。

于是，我们需要从单个用户的视角，切换到整台服务器的视角。

### 机器每秒完成多少工作？

在计算机系统中，我们通常用 **Throughput（吞吐量）**描述单位时间内完成的工作量。对普通 HTTP 服务，可以统计每秒完成多少个请求，也就是 Requests Per Second（RPS）。

LLM 推理服务当然也可以这样做，但有一个问题：回答一句“你好”，和阅读几千 Token 的论文并生成报告，虽然都算一个请求，消耗的计算资源却可能完全不同。

因此，还需要区分**输入 Token 吞吐量**和**输出 Token 吞吐量**。输入与输出 Token 对应的计算过程不同，即使都写成 tokens/s，也应该交代统计的是哪一种。

更容易混淆的是：**单个用户的输出速度，和整台服务器的总输出吞吐量，并不是一个指标。**

假设我们测试同一台服务器：

| 测试场景 | 单请求生成速度 | 服务器总输出吞吐量 |
| --- | ---: | ---: |
| 只有 1 个请求 | 50 tokens/s | 50 tokens/s |
| 同时处理 8 个请求 | 15 tokens/s | 120 tokens/s |

*这是为了说明指标差异而编造的教学数据，并非真实 Benchmark；第二行假设八个请求的生成过程充分重叠。*

在第二种场景下，每个用户的生成速度反而降低了，但整台服务器每秒生成的 Token 数量却从 50 增加到了 120。

那么，我们究竟优化成功了吗？

如果只关心单个用户的生成速度，显然没有；但如果希望有限的 GPU 能服务更多人，第二种配置就可能更有价值。

**提高系统整体吞吐量，不一定能够改善单个请求的延迟。**

这也是现代推理引擎需要处理的典型权衡：尽量让 GPU 有效地工作，同时避免请求因为排队或资源竞争而等得太久。

所以，看到一个惊人的 tokens/s 数字时，我们至少应该问：这是单请求速度，还是服务器总吞吐量？在什么输入长度、输出长度和请求负载下测出来的？<sup>[[2]](#ref-nvidia-benchmark)</sup>

## 为什么平均性能不能代表用户体验？

假设我们对实验室的推理服务发送了 100 个请求：

- 90 个请求在 100ms 后收到了第一个 Token。
- 剩下 10 个请求却等待了整整 5 秒。

如果计算平均 TTFT：

\[
\frac{90\times0.1+10\times5}{100}=0.59s
\]

平均等待时间为 590ms，看起来似乎还不错。

可是，对于那 10 个等待了 5 秒的用户来说，平均值没什么意义。他们只会觉得服务慢得令人难以忍受。

**平均值把一部分请求遭遇的严重延迟，掩盖在了大量正常请求之中。**

这并不是大语言模型特有的问题。事实上，早在大语言模型出现之前，互联网工程师就已经和它打了很多年交道。

### 一个来自互联网时代的老问题

2013 年，Google 的 Jeffrey Dean 和 Luiz André Barroso 发表了 *The Tail at Scale*，讨论大规模在线服务中的延迟问题。<sup>[[3]](#ref-tail-at-scale)</sup>

试想，一个搜索引擎需要同时向很多服务器查询数据，然后将结果汇总返回给用户。即使绝大多数服务器都能很快完成工作，只要有一台关键服务器异常缓慢，整个查询就可能被拖延。

我们甚至可以用一个简单的概率模型理解这种现象：假设一次查询需要等待 100 个彼此独立的子任务全部完成，每个子任务都有 95% 的概率按时结束，那么所有子任务都按时完成的概率只有

\[
0.95^{100}\approx0.59\%
\]

真实系统中的请求不一定相互独立，这也不是所有分布式查询的执行方式。这个例子只是说明：**局部少见的性能异常，可能在大规模系统中变成经常遇到的问题。**

延迟分布中那些特别慢的请求，就是所谓的 **Tail Latency（尾延迟）**。

那么，我们应该怎么描述它？

### 为什么工程师关心 P95？

统计学早就准备好了一个工具：**Percentile（百分位数）**。

把请求按照响应时间从短到长排列。如果某个服务的 P95 延迟为 1 秒，直观地说，就是约 95% 的请求能够在 1 秒内完成；P50 是中位数，P99 则观察更靠近分布尾部的位置。

回到刚才的例子：平均 TTFT 是 590ms，但 P95 TTFT 是 5 秒。这比平均值更直接地揭示了一批明显缓慢的请求。

百分位数并不是 SRE 发明的，只是随着大型互联网服务的发展，它成为了性能监控中的常用方法。Google 的 Site Reliability Engineering（SRE，站点可靠性工程）实践也强调，平均值可能掩盖尾延迟问题，观察分布往往更能反映用户体验。<sup>[[4]](#ref-sre-monitoring)</sup>

当然，P95 并不是万能的。它不能告诉我们最慢的 5% 究竟有多慢，更无法解释这些请求为什么慢；样本量过小时，高百分位数也可能很不稳定。

它只是观察延迟分布的一个切面，而不是优化目标本身。

回到 LLM 推理服务：有些用户只发一句问候，有些用户提交整篇论文；有些请求立即开始执行，有些请求需要等待其他请求释放资源。输入长度、排队时间和资源竞争，都可能使请求的延迟分布拉长。

因此，平均 TTFT 降低，并不意味着所有人都能更快看到第一个 Token；平均 TPOT 降低，也不意味着生成过程中不会出现卡顿。

更进一步，**平均延迟越低，服务就一定越好吗？**

假设一种配置能让少量请求获得极快响应，但在高负载下有明显长尾；另一种配置平均响应略慢，却能让绝大多数请求保持稳定。究竟应该选哪一种？

我们需要先确定：这个服务究竟希望达到什么水平。

## 更快，还是足够快？

假设我们给实验室的推理服务设定一个要求：

> 在预期的使用负载下，至少 95% 的请求应该在 2 秒内收到第一个 Token。

这不再是单纯的测量结果，而是可以检验的**服务目标**。在软件工程中，我们通常称它为 **Service Level Objective（SLO，服务等级目标）**。<sup>[[5]](#ref-sre-slo)</sup>

这里的 2 秒和 95% 只是教学示例，并非通用行业标准。

交互式聊天机器人可能非常关心 TTFT 和输出流畅度；夜间批量处理文档的任务，可能不要求这么快的首次响应，却希望尽可能利用现有算力。因此，我们不能脱离应用场景，直接判断某个 TTFT 或 TPOT 是否“合格”。

有了 SLO，性能评价也发生了变化。我们不再只是希望平均 TTFT 越低越好，而要追问：

**在满足服务质量要求的前提下，这台服务器究竟能够完成多少工作？**

## 吞吐量越高，服务能力就越强吗？

假设两台服务器运行相同模型、接受同一种工作负载。我们分别进行一分钟的压力测试：

| 指标 | 服务器 A | 服务器 B |
| --- | ---: | ---: |
| 完成请求数 | 1200 | 900 |
| 满足延迟要求的请求数 | 600 | 855 |
| 请求吞吐量 | 20 req/s | 15 req/s |
| 满足要求的请求比例 | 50% | 95% |

*以上是教学用的假设数据，并非真实 Benchmark。*

只看吞吐量，服务器 A 显然更快。但它完成的 1200 个请求中，只有一半满足我们设定的延迟要求。其他请求虽然成功返回了结果，却让用户等得太久。

反过来，服务器 B 的总吞吐量较低，却让更多请求满足了预期的服务质量。

我们不妨换一种统计方法：**只统计那些满足性能目标的请求**。

对这个例子，单位时间内满足要求的完成请求数，可以称为 **Goodput（有效吞吐量）**：

\[
Goodput=\frac{\text{满足延迟要求的完成请求数}}{\text{测量时间}}
\]

于是，服务器 A 的 Goodput 为 10 req/s，服务器 B 则是 14.25 req/s。

虽然 A 的总吞吐量更高，B 却完成了更多符合服务质量要求的请求。

**最大吞吐量，不一定对应最有价值的服务状态。**

Goodput 的思想也不是 LLM 出现以后才有的；在计算机网络中，它同样用于区分真正有效交付的工作和原始传输量。

2024 年发表于 OSDI 的 **DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving**，将 Goodput 作为 LLM 推理服务的重要优化目标。<sup>[[6]](#ref-distserve)</sup>

在 DistServe 的评估中，它被更具体地用于描述：在规定比例的请求同时满足 TTFT 和 TPOT 约束时，系统能够持续承受的最大请求到达速率。论文还通过按 GPU 数量归一化的方式比较资源效率。

这与刚才“某次测试中合格请求数除以时间”的简化计算并不完全相同，但它们想回答的是同一个工程问题：**怎样用有限资源，提供尽可能多符合预期的服务？**

Goodput 也不是一个可以脱离条件比较的数字。如果随意放宽延迟要求，更多请求自然会被算作合格；而满足延迟目标，也不意味着回答一定正确、完整或有用。模型质量、失败率和成本仍然需要单独考虑。

## 怎样证明我们的服务真的变快了？

到这里，我们已经知道，单独一个 tokens/s 或平均延迟，通常不足以描述一个推理服务。

但还有一个问题：如果某个引擎宣称自己比另一个引擎快了 50%，这个数字对我们的部署意味着什么？

它可能是正确的，却未必和我们的场景有关。

### 我们到底在测试什么？

同一台 GPU、同一个模型，如果分别处理两种请求，工作方式就可能非常不同：

- 简单问答：输入一句话，生成几十个 Token。
- 长文档总结：输入几千个 Token，生成一段长篇摘要。

两者都算一个请求，却有不同的计算需求。再加上不同的请求到达方式、上下文是否共享，测试结果还会进一步变化。

在性能评价中，我们通常用 **Workload（工作负载）**描述系统需要处理的工作及其到达方式。对于 LLM 推理服务，至少要交代输入长度、输出长度，以及请求如何到达。若存在大量共享前缀，还应该注意 Prefix Cache 对结果的影响。

这就像不能只凭汽车的最高速度，判断它在城市道路和山路上的实际表现。

### 并发数不等于请求到达速率

假设服务器能够同时处理 16 个请求。这既不意味着每秒一定有 16 个用户发来请求，也不意味着服务器每秒就能完成 16 个请求。

这里区分三件事就够了：

- **请求到达速率（Request Rate）**：客户端尝试以多快的速度发送请求。
- **并发数（Concurrency）**：某一时刻有多少请求尚未完成。
- **请求吞吐量（Request Throughput）**：服务器单位时间内实际完成多少请求。

如果服务器每秒稳定收到 10 个请求，却只能处理完成 8 个，而且没有拒绝或限流机制，尚未完成的请求就会不断积累。排队越来越长，TTFT 也可能随之上升。

反过来，如果请求到达得很稀疏，即使 GPU 还有不少空闲容量，也未必能测出最大吞吐量。

**请求来得多快，和系统做得多快，必须分别观察。**

### 做一次小型 Benchmark

vLLM 和 SGLang 都提供在线推理服务的 Benchmark 工具。它们可以模拟请求访问，并统计吞吐量、TTFT、TPOT 等指标。<sup>[[1]](#ref-vllm-benchmark)</sup><sup>[[7]](#ref-sglang-benchmark)</sup>

我们可以设计一个非常小的实验：**保持模型和硬件不变，只改变请求到达速率。**

例如，在一台满足运行条件的 GPU 服务器上启动 vLLM：

```bash
vllm serve Qwen/Qwen2.5-0.5B-Instruct
```

在另一个终端运行：

```bash
vllm bench serve \
  --backend openai \
  --base-url http://127.0.0.1:8000 \
  --model Qwen/Qwen2.5-0.5B-Instruct \
  --dataset-name random \
  --random-input-len 512 \
  --random-output-len 128 \
  --num-prompts 100 \
  --request-rate 1 \
  --percentile-metrics ttft,tpot,itl \
  --metric-percentiles 50,95,99
```

这组参数根据 vLLM 官方 Benchmark CLI 文档编写，实际使用时仍应以安装版本的 `vllm bench serve --help` 为准。它构造目标输入长度为 512 Tokens、目标输出长度为 128 Tokens 的随机请求，以平均每秒一个请求的速率发送测试流量。

`--request-rate 1` 控制的是请求**到达**速率，不是保证服务每秒完成一个请求；工具生成的到达间隔也不一定完全相等。输出长度可能受到提前停止生成等因素影响，因此还要检查实际生成的 Token 数量。

接着可以尝试把 `--request-rate` 改为 0.5、2、4，比较完成请求吞吐量和 TTFT、TPOT 的变化。这些数值只是演示档位，不代表这台服务器的实际容量。

你不妨先预测：

> 随着请求到达速率增加，服务器吞吐量会一直线性增长吗？用户看到第一个 Token 的等待时间又会怎样变化？

如果开始时服务器有大量空闲资源，增加请求可能让 GPU 工作得更加充分。但随着负载提高，系统迟早会遇到瓶颈。此时继续增加请求，可能不再获得同比例的吞吐提升，反而带来更长的等待。

究竟从哪里开始出现这种现象，需要实际测量，不能按预想的曲线编造结果。

还有两个限制需要说明。首先，100 个请求只能用于初步观察，不足以稳定估计 P99 等高百分位数。其次，有限个请求的压测结果，并不自动等于生产环境中能够长期维持的吞吐能力；正式评价应该增加样本量、重复测试并观察稳态。

如果希望进一步尝试“满足要求的请求吞吐量”，vLLM Benchmark 还提供了 `--goodput` 参数，可按 TTFT、TPOT 等请求级约束统计合格请求。这里同样要预先固定好 SLO，不能测完以后再调整标准。<sup>[[1]](#ref-vllm-benchmark)</sup>

### 什么样的比较才公平？

假设调优前后，两次 Benchmark 给出了不同的数字。想知道优化是否有效，至少应该确认：

模型和硬件是否相同？输入输出的长度分布是否一致？请求到达方式有没有变化？有没有缓存命中差异？比较的是推理引擎内部执行时间，还是经过 HTTP 服务后的客户端响应时间？

我们不必每次都模拟生产环境中的所有细节。为了研究某个机制，完全可以有意识地简化 Workload：例如固定其他条件，只改变输入长度，观察 TTFT 如何变化。

关键不在于运行了多少次命令，而在于：

**我们设计的实验能支持什么结论，又有哪些结论是它无法支持的。**

## 回到那台 GPU

再回到文章开头的三个抱怨。

有人说发送消息后要等很久才能看到回答。我们应该先观察 TTFT，并区分是长 Prompt、排队，还是其他开销造成的等待。

有人说模型回答到一半经常卡顿。我们应该看看输出 Token 的到达间隔，而不只是平均 TPOT。

有人说人一多服务就慢。我们应该同时观察请求到达速率、完成请求吞吐量，以及它们与延迟之间的关系。

如果我们准备长期提供这项服务，还需要问：**什么样的响应体验才算达到预期？** 有了明确的服务目标，才能进一步判断更多吞吐量是否真正转化成了更多有效服务。

归根结底，**推理服务的性能不是一个数字，而是一组相互制约的目标。**

更低的延迟、更高的吞吐量、更稳定的响应体验，未必能够同时获得；它们还取决于模型、硬件、工作负载和资源预算。

性能测量并不直接告诉我们该调哪个参数，但它让“优化成功了”成为一个可以用证据讨论的判断，而不是一句凭感觉说出的话。
