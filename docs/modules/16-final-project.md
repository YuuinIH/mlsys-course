# 16. 设计并为一个 ML 系统辩护

> 状态：占位。Part 6 · Design an ML System

## Design Brief

选择一个边界明确的训练或 serving 场景。项目目标不是堆叠最多工具，而是用证据提出并捍卫一套系统设计。

## 必交内容

1. workload characterization 与成功指标。
2. 至少两个关键资源或性能估算及其假设。
3. 一个 toy-scale, production-shaped 的实验和可复查结果。
4. 架构、数据 / 控制流和关键状态生命周期。
5. 瓶颈、故障域、恢复与可观测性设计。
6. 至少两个备选方案及 trade-off 表。
7. 最终 decision record 与重新评估条件。

## 允许的项目方向

- 训练 workload 从单卡扩到小型集群。
- 面向交互或批处理目标的 LLM serving。
- 多模态或 diffusion pipeline 的阶段设计。
- 有成本与 SLO 约束的共享推理平台。

## 评价标准

| 维度 | 权重 | 关注点 |
| --- | ---: | --- |
| 问题与 workload | 15% | 目标、边界和输入分布是否明确 |
| 测量与实验 | 25% | 证据是否可信、可复现、能证伪 |
| 机制与估算 | 20% | 是否解释关键约束并做 sanity check |
| 设计与取舍 | 25% | 方案是否匹配证据，代价与风险是否清楚 |
| 答辩与反思 | 15% | 能否回应反例并说明何时改变决策 |

工具数量、架构图复杂度和声称的“生产规模”不计分。小规模实验必须明确可迁移结论与规模限制。

## 答辩问题

- 哪项证据最可能推翻你的设计？
- 流量、模型大小或故障率提高十倍时，哪个假设先失效？
- 如果预算减少一半，你会保留什么、牺牲什么？
